## High-Level Findings

Oneesama now covers the main scanner and triage pipeline: 3 minute scanner cadence, 3-message cursor context, 5 minute conversation grouping, Cueboard-style digest lines, Pass 2 context expansion, durable triage contexts, SQLite/projection storage, audit endpoint, process health, and ACT/MAYBE/SKIP canaries.

The main uncovered risks are narrower than the earlier broad "triage feels thin" issue:

- P0: Cueboard suppresses scanner triage for threads already owned by the mention worker via `filterMentionedThreads`; Oneesama ignores direct bot mentions but does not yet suppress later non-mention replies in an active mention-owned thread.
- P1: Cueboard auto-joins public channels on `not_in_channel`; Oneesama only scans channels where the bot is already a member.
- P1: Cueboard periodically cleans stale scanner pending-action reservations; Oneesama has pending action flows, but no scanner-specific stale reservation cleanup hook in this slice.
- P1: Cueboard has a hard `triageToolCallMax=20` safety hook in the framework session; Oneesama's Codex/DeepSeek runner path has timeout/job handling but no equivalent per-triage tool-call counter.
- Product decision: Oneesama intentionally adds global/per-channel 429 backoff and process-health auditing; Cueboard relied mainly on 3 minute cadence.

## P0 Gaps

- `scanner.go:351-381 filterMentionedThreads` is missing in Oneesama scanner/inbound paths. Direct bot mentions are ignored, but later non-mention replies inside a thread already being handled by the mention queue can still be swept into triage. Suggested implementation location: `service_inbound.go` or `inbound_buffer.go`, using the existing mention-thread queue/ledger state.

## P1 Gaps

- `scanner.go:69-80 cleanupScannerReservations` has no scanner-specific stale pending-action reservation cleanup. Suggested location: pending-action service or scanner startup tick, with tests proving stale scanner reservations are cleared without touching active user-confirmable actions.
- `scanner.go:329-349 getConversationHistoryWithJoin` behavior is not equivalent. Cueboard auto-joins on `not_in_channel`; Oneesama filters `conversations.list` to `is_member` and scans only joined channels. Product decision needed: keep quiet member-only behavior, or add safe public-channel join/backoff.
- `scanner_triage.go:133-147 newTriageHooks` has no direct `triageToolCallMax=20` safety counter in the Codex/DeepSeek runner path. Existing timeout/job boundaries help, but a runaway tool loop would not be cut by the same guard.
- `scanner.go:235-286 collectChannelMessages` / `scanner_event.go:203-270 reconcileChannel` bootstrap behavior differs: Cueboard initial window is 24h; Oneesama uses 10m and commits the first cursor without buffering. That is safer for production noise, but it is a parity drift that should be documented as a product choice.

## Product Exclusions

- Cueboard hidden framework session functions (`createTriageSession`, `executeTriageSession`, `deleteTriageSession`, `buildTriageMessage`) are intentionally replaced by Oneesama's service-level agent runner and JSON decision adapter.
- `reverseMessages` is unnecessary because Oneesama sorts by Slack timestamp.

## Open Questions

- Should Oneesama intentionally keep member-only scanner scope, or should it match Cueboard's auto-join behavior for public channels?
- Should the 10m bootstrap lookback stay as a production safety choice, or should there be a first-run backfill mode for parity/audit environments?
- Should mention-owned thread suppression be keyed only on currently running mention jobs, or also on recent handled mention ledger entries for a grace window?
