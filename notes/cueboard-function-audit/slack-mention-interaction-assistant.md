## High-Level Findings

Oneesama covers the baseline Slack mention and interaction surface: Events API / Socket Mode dispatch, rich thread transcript construction, Slack `conversations.replies` fetch, external link enrichment, assistant status shimmer, pending-action cards, join-card interactions, reply feedback, emoji feedback, and feedback memory persistence.

The main risk is that several Cueboard mechanisms were ported as isolated helpers or tests but are not yet connected to the live mention runtime:

- P0: Cueboard serializes mentions per thread and suppresses stale replies; Oneesama defines `slackMentionQueue`, but the live app-mention handler never enqueues/dequeues it.
- P0: Cueboard registers an active mention thread so assistant Slack API calls cannot post into the same thread; Oneesama has a dormant `slackAPITool.activeThread` hook but no active-thread registry is wired into the tool registry.
- P1: Cueboard forwards incremental assistant history into the Slack thread; Oneesama has a forwarder helper and tests, but no live history listener / flush path.
- P1: Cueboard fetches live meeting captions for the Slack thread; Oneesama only uses meeting context included in the event payload.
- P1: Cueboard fetches Slack Canvas content into mention context; Oneesama detects Canvas references but does not download Slack Canvas body text.
- P1: Cueboard updates or strips interactive action blocks after decisions; Oneesama often returns only an ephemeral acknowledgement, so old pending-action cards can remain visually actionable.
- P1: Oneesama durable context treats any ledger summary as a recent handled task, while Cueboard only injects summaries that look like actual handled work.

- `mention_context.go:532-567`: live meeting context is not fetched by Slack thread. Oneesama should query its meeting store / meeting-agent by `(channel_id, thread_ts)` and inject recent captions/speakers when a Slack thread has an active Meet. **Still open.**

Wiring the same fetcher into `buildSlackAppMentionContext` so a Canvas-comment mention auto-inlines Canvas text without an extra tool call is still open.
- ~~`interaction.go:37-76` and `763-819`: pending action cards are not consistently updated after confirm/dismiss/feedback.~~ **RESOLVED** (commit `495bbd0`): driver landed card replace-on-decision for confirm/dismiss.
- `interaction.go:136-195` / `425-441`: pending-action confirmation only executes `join_meeting`. Confirmed `create_channel` is a real missing Slack-side side effect; direct Linear/Calendar action execution remains product-excluded. **Open product decision** (see Open Questions).
- ~~`assistant_context.go:159-195`: durable context should reuse Cueboard's `looksLikeHandledTaskSummary` guard.~~ **RESOLVED** (commit `1539917`): `formatSlackDurableContext` now demotes SKIP / failed / observed ledger summaries to "recent thread note" instead of "recent handled task", and rejects "SKIP:" / "No action needed" prefix patterns.

## Product Exclusions

- Direct Linear issue creation/commenting and direct Google Calendar event creation are still intentionally excluded from Oneesama's production tool surface. This keeps task #147's isolation/de-scoping decision intact.
- Proactive reply-feedback footer UI is intentionally removed after Peng called it annoying. Feedback capture now lives through legacy feedback interactions plus emoji-key analysis.
- Cueboard framework-session types, hidden session listeners, and `agent.TextResult` wrappers are replaced by Oneesama's service-level agent runner and typed HTTP handlers.

## Open Questions

- Should Oneesama restore Cueboard's incremental Slack mention streaming, or is final-response-only the desired product behavior now that Realtime/worker handoff exists?
- Should `create_channel` confirmation be implemented as a Slack-side mutation, or should `suggest_action(create_channel)` be disabled until there is a safe confirmation/update-card path?
- Should mention-owned thread suppression from task #163 key off the live mention queue only, or also off a short-lived active-thread registry after worker completion?
