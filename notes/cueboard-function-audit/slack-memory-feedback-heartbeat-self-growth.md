## High-Level Findings

- **P0 trigger gap (matches the operator-observed empty SQLite tables):** Oneesama writes feedback (`recordFeedbackMemory`), reactions, and inbound user-text improvement signals, and Cueboard's `MEMORY.md` self-growth block + lesson candidate files are wired through `syncImprovementArtifacts`. However, `recordImprovementSignals` stops after `improvements.InsertSignal` + `syncImprovementCluster` and never lands rows in any auditable `improvement_signal` collection — and `improvement_signal` / `heartbeat_followup` / `feedback_entry` SQLite tables are 0 since 5/12 according to the prior audit. The Cueboard-style `BuildHeartbeatContext → ListPendingHeartbeatFollowups → followups surfaced via heartbeat ticks` loop is **completely missing**: Oneesama only surfaces follow-ups when `SurfaceSlackFollowups` is called externally (HTTP/tool), and there is **no periodic heartbeat tick** that flushes `next_check_at`-eligible follow-ups. Operators should consider this a _cold runtime_: rows can be inserted but nothing surfaces them on a cadence.
- **P0 self-growth schedule normalization is unported:** `(*Bridge).PrimeHeartbeatState`, `normalizeThreadCommitmentFollowups`, `normalizeLegacyHeartbeatSchedules`, `syncPendingActionHeartbeatFollowups`, `syncImprovementHeartbeatFollowups`, `ensurePendingActionDecisionFollowup`, `resolvePendingActionDecisionFollowup`, `cleanupStalePendingActionFollowups`, and `maybeRecordAssistantCommitmentFollowup` have **no Oneesama equivalent**. This means: pending-action confirmations don't enqueue auto-followups, stale `pending_action:*` followups never get cleaned, duplicate thread-commitment followups never merge, and `next_check_at` is never backfilled on legacy rows. Cluster sync from open improvement signals does run (`syncImprovementCluster`), but it only fires inline when a new signal is inserted — it does not periodically re-sync.
- **P1 heartbeat delivery callback path absent:** Cueboard's framework-driven `slackHeartbeatListener.OnHeartbeatResult → (*Bridge).handleHeartbeatResult → deliverHeartbeatNotification` pipeline (with `recordHeartbeatSnapshot`, supervisory-completion suppression, DM fallback retries, 15s context timeout) does not exist. Oneesama replaces it with `Service.SurfaceSlackFollowups → surfaceOneFollowup`, which is structurally similar but only runs when invoked. There is no `heartbeatRuntimeSnapshot` runtime state (the heartbeat fields in `runtime_status.go` are best-effort and not written by a heartbeat callback). `requestImmediateHeartbeatIfPending` and `heartbeatNotificationMentionsDoneSignal` / `heartbeatNotificationSoundsLikeSupervisionClosure` are also missing.
- **P1 store API surface narrower than Cueboard:** Oneesama's `slackHeartbeatStore` exposes `CreateFollowup`/`UpdateFollowup`/`ResolveFollowup`/`ListFollowups`/`RecordSurface`/`ListSurfaces`/`CountRecentPublicHeartbeatSurfaces`. The Cueboard-specific helpers `GetHeartbeatFollowupBySourceRef`, `TouchHeartbeatFollowupSurfaced`, `CountOpenHeartbeatFollowupsByKind`, `CountHeartbeatFollowupsByMetadataMarker`, `CountPendingHeartbeatFollowups[ForSource]`, `ListOpenHeartbeatFollowups`, `ListPendingHeartbeatFollowups[ForSource]`, `ListRecentHeartbeatSurfacesForSource`, and the canonical-thread-commitment dedup walker `findCanonicalHeartbeatFollowupID` are all **missing**. The improvement store loses `ListSignals` (by `since`), `CountOpen`, `ListRecentImprovementTopicCounts`, `CountDistinctImprovementThreads`, `UpdateImprovementSignalsForCluster`, and `GetImprovementSignal`. The feedback store loses `ListFeedbackEntriesByDates` (only `ListEntries` exists; the date-range read path used by `loadRecentFeedbackDays` is gone, replaced by `RecentMarkdown` which simply tail-limits).
- **P1 heartbeat context narrower than Cueboard:** Oneesama's `BuildHeartbeatContext` returns the same five sections (candidates, follow-ups, recent threads, meeting carry-overs, recent surfaces) but **drops the upcoming-deadlines + Google Calendar section** entirely (`formatHeartbeatUpcomingDigest`, `summarizeUpcomingFollowupDeadlines`, `formatCalendarEventStart`, gcal calls). Candidate selection is also flatter: `selectHeartbeatCandidates` ranking by kind/priority/signal-count/explicit-request is reduced to "top N from open list, ordered by next_check_at/due_at/updated_at". So the "self-growth-aware candidate ranking" Cueboard does is not reproduced.
- **Product decision: Cueboard `slack_heartbeat` framework-session ABI is intentionally excluded.** Tool wrappers (`(*followupMemoryTool).Name/Description/Parameters/Execute/record/resolveSource/resolve/keepSupervisoryCommitmentOpen/applyMessageRefSource/fillSourceThreadFromChannel/handleSelfImprovementResolution`, `(*heartbeatLogTool).Name/Description/Parameters/Execute`, `(*personMemoryTool).Name/Description/Parameters/Execute`) are gone because Oneesama dispatches tools through `slack_tool_registry.go`'s `ExecuteSlackTool` rather than via `agent.Tool` interface implementations. Same for the Cueboard `slackHeartbeatListener` adapter. Behavior is preserved (record/list/resolve flows) but the per-method tool spec lives in the registry, not as struct methods.
- **Product decision: emoji feedback widened.** Oneesama recognizes a richer emoji set (`feedbackKindForReactionEmoji`) than Cueboard's reply-feedback button-only model and adds a new wired path: `service_events.go → handleReactionFeedbackEvent → emojiFeedbackFromReactionEvent → recordFeedbackMemory + recordEmojiFeedbackImprovement`. Cueboard's `improvement_self_growth.go` only fires improvement signals on inbound user text. This is a feature addition documented in commit `3a0aee7 fix(slack): learn feedback from emoji reactions`.
