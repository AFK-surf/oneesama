## High-Level Findings

- **P0 persistence schema gap (matches `Stats()` log line "0 channels, 0 memberships, 0 cases"):** Cueboard's SQLite schema has four tables that Oneesama does not maintain at all: `channel`, `channel_membership`, `thread_case`, and `thread_recommendation`. Oneesama's `slackCognitionStore` only covers `slack_channel_brain` + `slack_thread_ledger`, and pending/outbound action stores cover the `pending_action` and `outbound_action` rows. As a result, `UpsertChannel`, `SyncChannelMembers`, `ListChannels`, `ListChannelIDs`, `ListChannelMemberIDs`, `UpsertThreadCase`, `GetThreadCase`, and `ReserveRecommendation`/`ConfirmRecommendation`/`FailRecommendation`/`CleanupStalePendingRecommendations` are all missing from this slice. Oneesama's scanner relies on Slack-API channel listings + an `is_member` filter, not a persisted membership table, so workspace bootstrap reads less state than Cueboard.

  **Phase 1 update (2026-05-18):** Three of the four tables are now persisted as Oneesama `persistence.TypedCollection` rows:

  - `channel` → `slack_channels` (`workspace_state_store.go`, methods `UpsertChannel` / `ListChannels` / `ListChannelIDs`).
  - `channel_membership` → `slack_channel_membership` (`workspace_state_store.go`, methods `SyncChannelMembers` / `ListChannelMemberIDs`).
  - `thread_case` → `slack_thread_cases` (`thread_case_store.go`, methods `UpsertThreadCase` / `GetThreadCase` / `MarkClosed` / `IsActive`).

  The scanner's `listSlackScannerChannels` now upserts every observed channel into the durable store (`persistScannerChannel` hook), and the `Status()` JSON includes `workspace_state` + `thread_cases` counters so the empty-table operator finding will surface as nonzero on the next sweep. `thread_recommendation` plus the Recommendation Confirm/Fail/Cleanup helpers remain missing and are tracked under the consolidated backlog Phase 3 (real `suggest_action` side effects).

- **P0 cursor durability regression (fixed in Phase 1):** Cueboard's `event_cursor` table persists `SetEventCursor`/`GetEventCursor`, so the scanner is restart-safe per channel. Oneesama now mirrors that with `slack_scanner_cursors` (`scanner_cursor_store.go`): `NewService` rehydrates persisted cursors into the inbound buffer on startup, and scanner/sweep cursor advances flow through `setInboundCursor`.

- **P0 SQLite ABI and operational tooling absent:** `NewStore`/`Close`/`migrate`/`ensureColumn` plus the WAL `prepareSQLitePath` + `refreshSQLiteRecoverySnapshot` call chain are not ported. Oneesama abstracts persistence behind `persistence.TypedCollection`, so there is no schema migration script, no `journal_mode=WAL`/`busy_timeout=5000` tuning, no `_recovery` snapshot, and no per-startup migration log. Operationally this means: the data shape is JSON in either `memory` (memdb) or per-collection SQLite files, but the dedicated `slack.db` and its ALTER-TABLE-driven evolution path are gone. This is intentional but should be tracked because it directly drives the empty-tables ops finding.

- **P1 DM / debug-channel posters missing:** `openDM`, `postDM`, `postDMInThread`, `postDebugChannel`, `postDebugChannelThread`, `postDebugChannelBlocks`, `postDebugChannelThreadBlocks`, and the persistent `b.dmChannelID` cache have **no Oneesama equivalent**. `Poster.PostMessage` is the only generic outbound poster. The `PilotUserID` + `DebugChannelID` config keys are also gone — Oneesama's `pkg/config.SlackConfig` has no analog. So heartbeat surface fall-back-to-DM and any "send to operator DM/debug channel" diagnostic flow is structurally absent.

- **P1 admin dashboard intentionally excluded but the audit endpoints are narrower:** 184 `product_excluded` functions across `admin*.go` and `admin_templates*.go` represent the entire HTML admin cockpit (`/admin/page`, `/admin/tab`, `/admin/triage/lookup`, `/admin/people/correction`, `/admin/memory/*`, `/admin/meetings`, `/admin/logs`, presence dashboard, debug log, runtime status). Oneesama replaces all of this with a small set of internal-auth JSON endpoints in `handler.go`: `/inbound/status`, `/inbound/flush`, `/scanner/sweep`, `/scanner/compact`, `/triage/status`, `/triage/audit`, `/triage/run`, `/triage/probe`, `/followups/status`, `/followups/create`, `/followups/surface`, `/heartbeat/context`. This is the right product call (HTML admin was a Cueboard-only ops console), but the `presence` view + `triage/lookup` permalink search + `memory` directory browser + `people/correction` write path are real Cueboard surfaces that Oneesama operators currently have no equivalent for.

- **P1 config schema narrower than Cueboard:** Cueboard `Config` has 30+ fields (Linear, Google Calendar with primary/visible fallback, Figma, Notion, Meet webhook + approval channel, debug channel, pilot user, LLM/MeetCopilot model names, repo runtime/worktree dirs, scanner mode/debounce/max-batch). Oneesama `pkg/config.Config` is structured around `SlackAgent`/`MeetingAgent`/`Slack`/`AgentRunner`/`Meetd`/`OpenAI`/`Dialog`/`Logging`/`Paths`/`Persistence`. Many Cueboard knobs intentionally have no Oneesama analog (Linear/Google/Figma/Notion/MeetCopilotModel) because those integrations are decomposed differently. But `PilotUserID`, `DebugChannelID`, `RepoRuntimeDir`/`RepoWorktreeDir`, scanner mode/debounce/max-batch are real operator-tunable knobs whose absence has product impact.

- **Product decision: Cueboard's structured meetings store (`meeting_thread`, `meeting_result_delivery`) is partially ported through `meetingWebhookStore`**, which only covers `GetThreadByRemoteID`/`InsertThread`/`ReserveResult`/`ConfirmResult`/`FailResult`/`ResetResult`/`CleanupStaleReservations`. The Cueboard helpers `GetMeetingThread(dedupeKey)`, `GetMeetingThreadBySlack(channelID, threadTS)`, `UpdateMeetingThreadRemoteID(dedupeKey, remoteMeetingID)`, and `ListMeetingThreads()` are missing — the in-meeting "look up by slack channel" path is absent, which limits cross-channel idempotency.

## P0 Gaps

- **`channel` / `channel_membership` / `thread_case` / `thread_recommendation` tables are not modeled in Oneesama.** Suggested location: a new `slack_workspace_store` collection group (or extend `slackCognitionStore`). Without `channel_membership`, the scanner cannot rely on persisted workspace state to detect added members; without `thread_case`, the mention-thread queue has no durable record of who claimed which thread; without `thread_recommendation`, "we already posted a recommendation in this thread" is not enforceable across restarts. Likely fix: add `slack_channels` / `slack_channel_membership` / `slack_thread_cases` / `slack_thread_recommendations` `TypedCollection` collections and back the corresponding cueboard helpers.
- **`event_cursor` table is replaced by an in-memory map.** Suggested location: persist `s.inbound.Cursor`/`SetCursor` through a new `slack_scanner_cursors` collection so that scanner restart is non-lossy.
- **`Stats()` log line `slack store: N channels, M memberships, C cases` is gone.** Once `channel`/`channel_membership`/`thread_case` are persisted, restore a similar startup log (this is the operator-visible signal flagged in the prior live audit).
- **SQLite migration ABI absent (`migrate`, `ensureColumn`, ALTER TABLE flow).** This is the right product call for the new persistence shape, but blocks any incremental migration from a legacy `slack.db`. If the rollout plan involves importing from Cueboard SQLite, an import script is needed.

## P1 Gaps

- **DM and debug-channel posters missing (`openDM`, `postDM`, `postDMInThread`, `postDebugChannel*`).** Suggested location: a `service_dm.go` that wraps `Poster.PostMessage` with a cached `dmChannelID` map keyed by `PilotUserID`. Cueboard heartbeat surface fallback ("if public-channel post blocked, DM the pilot") was a core safety net.
- **`PilotUserID` and `DebugChannelID` config keys missing.** Suggested location: `pkg/config.SlackConfig`. Needed before DM posters can be re-introduced.
- **Meeting thread lookups by dedupe key and by `(channel, thread)` are missing (`GetMeetingThread`, `GetMeetingThreadBySlack`, `UpdateMeetingThreadRemoteID`, `ListMeetingThreads`).** Suggested location: `meeting_webhook_store.go`. Without `GetMeetingThreadBySlack` the in-Slack interactive "remember which meeting this thread is for" loop has no idempotent backstop.
- **`DeleteOutboundActionByReference` missing.** Suggested location: `heartbeat_store_actions.go`. Cueboard uses it to clean up outbound actions when a higher-level entity (e.g. linear issue) is rolled back.
- **`getPermalink` central helper missing.** Suggested location: `slack_thread_fetch.go` or a small helper file. The "channel:ts" fallback string when `chat.getPermalink` fails is currently inlined per-caller.

## Product Exclusions

- Entire `admin*.go` + `admin_templates*.go` HTML cockpit (184 functions). Replaced by a small set of JSON internal-auth endpoints. Permanent product decision.
- Cueboard config keys with no Oneesama analog (intentional decompose): `LLM_MODEL`, `MeetCopilotModel`, `LINEAR_*`, `GOOGLE_CALENDAR_*`, `FIGMA_API_KEY`, `NOTION_TOKEN`, `MEET_APPROVAL_CHANNEL`, `MEET_AGENTD_URL`, `MEET_WEBHOOK_LISTEN`. These integrations are not part of the Oneesama Slack agent service.
- `nullableTimePtr`, `compareInts`, `compareBoolDesc`, `presenceMin` — small adapters whose roles are replaced by Go 1.21+ builtins / RFC3339 string handling.

## Open Questions

- Should `channel`, `channel_membership`, `thread_case`, `thread_recommendation`, and `event_cursor` be brought back as `TypedCollection`s, or is the runtime architecture intentionally moving away from persisted workspace state? If the latter, the `Stats` log line and operator expectations need explicit documentation.
- Should `PilotUserID` + `DebugChannelID` be re-introduced, or is the new design that operator notifications go through the heartbeat surfacing path only (no direct DM)?
- Should there be an importer from legacy Cueboard `slack.db` into the new `TypedCollection` files, or do operators start fresh? Either way the schema-migration story is not yet documented in `docs/adr/`.
