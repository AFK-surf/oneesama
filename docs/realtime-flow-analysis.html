Realtime system map

它为什么脆弱

当前 Realtime 不是一条单纯的“语音模型接 Meet”链路，而是把 WebRTC、Meet DOM、头像、 app 分享、Computer Use、后台 worker、Meet chat 和 session 清理都塞进同一个实时回路。 真正的问题不是某一个 bug，而是多个异步系统在用 prompt 和 heuristics 勉强同步。

当前健康判断

1 一个浏览器 bridge 同时管连接、音频、工具、worker、chat、screen share、diagnostics。
3 至少三个时钟：Realtime event clock、Meet browser clock、Go/worker clock。
4+ 可见输出通道：voice、Meet chat、screen/app share、worker result、avatar HUD。
已起步 现在已有 typed turn policy / meeting event，并新增 failure matrix 暴露真正卡点。

主流程

这是现在真实跑起来的一条链路。每个格子都不是抽象概念，而是代码里已有的边界或注入点。

Join / Boot

1. Slack / API 触发 Join

/join/google-meet 进入 Go service，先停重叠 session，再准备 meet-runner 参数。

2. Go 调 meet-runner

PrepareGoogleMeet 带上 Realtime、worker poll、screen share、browser args 等十几组开关。

3. Playwright 打开 Meet

Chromium 进会，填名字、点 Join，并在导航前注入头像、Realtime、worker、screen share 脚本。

4. Session 记录启动

Go DB 保存 session；monitor goroutine 轮询 runner 状态，但页面内状态仍由浏览器自己维护。

Realtime Core

5. Mint client secret

/realtime/client-secret 用工具 schema、instructions、voice、turn detection 生成 session。

6. Browser bridge 建 WebRTC

页面内建 RTCPeerConnection，转发 Meet audio，打开 data channel，发送 session.update。

7. 监听 Realtime event

处理 response.created、音频 delta、speech_started、tool call、response done。

8. Input gate / cancel

用户讲话时尝试 response.cancel，并用 gate 控制什么时候重新收音。

Tool Branches

9A. Meet tools

发 Meet chat、读 chat、看 participants、present/stop stage、share existing app window。

9B. Workspace / app control

control_shared_app_window 通过 KWWK/Codex backend 排队或等待执行，默认异步。

9C. Worker

Realtime 可 delegate；Go 也会把 meeting-scoped worker result 注入页面或发到 Meet chat。

9D. Avatar / memory / fetch

同一个 Realtime session 还拥有头像动作、memory、URL fetch、Slack/Notion/GitHub 查询工具。

Return / Cleanup

10. Tool result 回写

页面发送 function_call_output，很多分支会自动追加 response.create。

11. 可见输出

模型可能说话，也可能发 Meet chat、更新分享画面、显示 avatar HUD、或被要求保持 silent。

12. Status refresh

Go 通过 runner status 把 browser runtime state 压缩回 /join/status。

13. Stop / terminal

stop、removed、stale、restart 都必须同时收掉 Meet、screen share、worker poll 和 active response。

三个异步时钟

脆弱感的根因在这里：系统经常把“某个时钟成功”误读成“整条链路完成”。

Realtime event clock

  1. server 产生语音、function_call、response.done。
  2. data channel 收到事件后页面本地处理。
  3. tool result 回传后可能立刻触发下一轮 response。
风险：模型听到“工具 accepted”就开始口头总结，但真实 app 操作可能还在队列里。

Meet browser clock

  1. Playwright 页面进入 Meet，DOM 状态随 Google UI 改。
  2. 音频、字幕、chat、screen share 都在页面内观测。
  3. ScreenCaptureKit / MJPEG / canvas 再转成 Meet 里可见的 stream。
风险：sender 侧 active 不等于 receiver 侧看见，真实验收必须看浏览器 consumer。

Go / worker clock

  1. Go 持有 session DB、worker queue、tool HTTP handlers。
  2. worker result 可能从 HTTP 注入，也可能由页面 poll。
  3. join status / cleanup 依赖 runner 状态刷新。
风险：session 已 terminal 但 poller、screen share、worker result 某条支线还活着。

Failure matrix

新版 feedback 不再只给一个“ready / waiting / blocked”摘要，而是按五个子系统给出状态。 这能避免“本地 mic fallback 算输入”“工具 pending 被 remote audio blocker 掩盖”这类误诊。

主要脆弱点

按“会导致 Peng 体感失败”的优先级排序，不是纯代码洁癖。

P0 Tool result 没有统一出口政策

每个 tool branch 自己决定是否 response.create、说什么、是否沉默。 结果就是一个修复常常只覆盖某个工具，换到 worker result 或 app-control 又开始乱讲话。

realtime-browser-bridge.ts: sendFunctionCallOutput / shouldAutoRespondToMeetToolResult / handleLocalToolCallEvent / injectWorkerResult

P0 App control 是异步任务，却被语音当同步动作

control_shared_app_window 默认排队返回 job_id，真实点击/输入还没结束。 现在靠 prompt 告诉模型“不要 claim completion”，这太软，应该变成协议层状态。

realtime_app_control.go: ControlRealtimeSharedApp；realtime_tools.go: control_shared_app_window schema

P0 Worker result 有多条注入通道

Go 的 deliverWorkerReportRealtime 会注入到 meet-runner；页面里还有 worker-result bridge poller。 近期已经靠 session/source 过滤止血，但架构上仍然容易重复、串线或晚到。

service_worker_realtime.go；google-meet-joiner.ts: injectWorkerResult；worker-result-bridge.ts

P0 Realtime bridge 过大，状态边界混在一起

一个 4000+ 行 browser bridge 同时管 WebRTC、VAD/cancel、tool router、Meet chat、 avatar、worker、diagnostics。任何小改动都可能影响另一条用户路径。

packages/core/src/realtime/realtime-browser-bridge.ts: legacy baseline 2559 lines, plus extracted helpers.

P1 raw WebRTC 和 Agents SDK 两套运行时语义不一致

raw path 发送 response.cancel；Agents SDK path 走 session.interrupt。 tool、cancel、reconnect 的状态不是同一个抽象，调一个 path 不代表另一个 path 安全。

realtime-browser-bridge.ts: connectRealtimeAgentSDK / connectRealtime / cancelActiveResponse

P1 可见 share 成功依赖嵌套 heuristic

app-share 成功后是否沉默现在靠在 result 里找多层 screenShare.active。 这比 typed presentation state 脆弱，后端返回结构一变就误说或误沉默。

realtime-browser-bridge.ts: resultHasActiveScreenShare / shouldAutoRespondToMeetToolResult

P1 session state 分裂

Go DB、meet-runner active record、browser page state、Realtime connection 都各自有“活着/死了”的判断。 如果 stop 没穿透每层，就会出现分享还在、poller 还在、join/status 却说 inactive。

service_join.go: JoinStatus / sessionFromRuntimeStatus；google-meet-joiner.ts: refreshActiveRuntimeState

P1 工具面太宽，模型路由成本太高

同一个 session 暴露 app share、browser workspace、create workspace、fetch、Linear、Slack、Notion、 GitHub、memory、avatar。再加 compatibility aliases，模型很容易选错路径。

realtime_tools.go: defaultRealtimeToolDefinitions

应该变成什么

别再靠“这次 prompt 多写一句”续命。要把实时系统拆成几个硬边界。

现在的形状

  • tool handler 自己决定 spoken follow-up。
  • 异步 job 返回值和完成值混在一个 tool output 里。
  • screen share、worker、Meet chat、voice 都能各自触发下一轮模型。
  • browser bridge 是总控台，也是运输层，也是产品策略层。
  • 状态靠 diagnostics 和局部 postcheck 拼起来。

目标形状

  • 统一 RealtimeTurnPolicy 决定 voice / Meet chat / visual-only / silent / blocked。
  • 所有副作用输出统一包成 typed MeetingEvent，带 session、turn、visibility、interruptible。
  • app-control 变成 accepted → running → completed/blocked 状态机。
  • browser bridge 拆成 transport、audio、tool-router、meet-chat、worker-results、presentation-state。
  • Go service 成为 terminal cleanup 的唯一 owner。

重构路线

按可落地顺序来，先收最影响 demo 体感的口子。

收口 tool result policy

新增一个中心函数，例如 deliverToolResult()。所有 worker / meet / workspace / avatar 工具都只返回事实， 由 policy 决定是否发语音、Meet chat、或静默。

把 app-control job 协议硬化

control_shared_app_window 的第一次返回只能是 accepted/running，不允许模型口头总结完成。 completed/blocked 由 job event 单独注入，且默认 Meet chat 简报优先于长语音。

合并 worker result 通道

选一个主通道。建议 Go service 写入 session-scoped event queue，页面只消费 queue； 移除“双注入 + poller markDelivered”这种竞态结构。

拆 browser bridge

先切文件，不改行为：transport、audio-gate、tool-router、presentation-state、worker-results。 拆完再对每层加 targeted smoke，避免继续在 4000 行文件里打补丁。

必须保留的回归门

以后每次动 Realtime，不应该只看后端 green，要看这些用户体感门。

打断门

让 bot 说长 worker/result 总结时真人插话，必须能 cancel 当前输出，后续仍能继续听。

可见分享门

share Pencil / VS Code / generic editor / URL / create workspace / stop，receiver 端必须可见。

chat-vs-voice 门

worker result 长内容必须进 Meet chat；voice 只说一句“我发到聊天里了”。

session scoping 门

Slack triage、secretary、旧 meeting worker result 不得注入当前 Realtime。

terminal cleanup 门

stop / removed / restart 后，join/status、browser process、screen share、poller 全部归零。

consumer rendering 门

屏幕分享不只看 sender FPS，还要看 Meet receiver 端真实画面，尤其文字清晰度。

一句话结论： Realtime 现在脆弱，是因为它把“实时对话系统”和“后台 agent 操作系统”混在同一个模型回合里， 还允许多个输出通道各自触发下一轮模型。下一步最值得做的不是继续补单点 bug， 而是先用 failure matrix 把卡点显性化，再继续把 app-control / worker / presentation 收进 typed event state machine。
