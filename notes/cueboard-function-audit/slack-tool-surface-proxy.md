## High-Level Findings

Oneesama has a much clearer tool visibility layer than Cueboard did: `/slack/tools/parity` reports active/stub/excluded tools, `/slack/tools/call` and `/tools/call` provide a loopback gateway, and the current registry lists product exclusions explicitly instead of silently hiding credentialed integrations.

The active surface is still not as complete as Cueboard's runtime behavior:

- P0: `suggest_action` is advertised as active, but the `/slack/tools/call` implementation only validates and returns a normalized request. It does not reserve a recommendation, insert a pending action, post the Slack confirmation card, attach the card timestamp, or create the decision follow-up that Cueboard's `suggestActionTool.Execute` performs.
- P0: `slack_api` still has a dormant active-thread guard. Cueboard wires `Bridge.hasActiveThread` into `chat.postMessage` so assistants cannot tool-post into the thread they are already answering; Oneesama defines `activeThread` on `slackAPITool`, but `Service.executeSlackAPITool` never sets it.
- P1: Slack API parity is uneven. Text posting, thread fetch, channel history, upload, and generic form mutations exist; `slack.fetchImage`, `slack.fetchCanvas`, `canvases.create`, `canvases.edit`, and `slack.sendDM` are registered as unavailable.
- P1: Cueboard post-side effects are missing from Oneesama's gateway path: no outbound reservation/dedupe for `post_thread_reply`, no Block Kit `blocks` validation/rendering for `chat.postMessage`, no thread-ledger recording, and no mutation/failure counter hooks for the loopback tool gateway.
- P1: `runtime_status`, `heartbeat_log`, `usage_api`, and `notify_meeting_slack` are visible, but they are thinner than Cueboard's tools. In particular, `runtime_status(action=...)` is not honored by `ExecuteSlackTool`, `usage_api` is a stub, and `notify_meeting_slack` posts raw channel/thread text instead of resolving linked meeting threads and Slack user mentions.

- `notify_meeting_slack` should resolve the current meeting's linked Slack thread and mention user IDs by channel membership/name matching. The current gateway version accepts raw channel/thread/text and loses Cueboard's dedupe/user-resolution safety.
- ~~`slack_api(add_reaction)` should restore Cueboard's digest `message_ref` / latest-message target resolution if the triage runner is expected to react using digest refs.~~ **RESOLVED** (`a3913d5`): `add_reaction` now accepts `message_ref` / `target_ref`, parses scanner digest refs, falls back to the latest digest message for a channel, normalizes emoji names, and treats Slack `already_reacted` as success.

## Product Exclusions

- Direct credentialed proxies remain intentionally excluded: `linear_api`, `google_calendar_api`, `figma_api`, and `notion_api`.
- Direct generation helpers remain intentionally excluded: `image_generation` and `audio_generation`.
- Direct Meet chat sending remains intentionally excluded: `send_meeting_chat`.
- Legacy `run_command` is not exposed by Cueboard's default Slack registration anymore and is not ported as a Oneesama Slack tool. If Debug Sprint / Computer Use work later needs host commands, it should use the new explicit safety model instead of resurrecting this hidden Slack utility.

## Open Questions

- Should `suggest_action` become a real side-effecting tool again, or should Oneesama keep pending-action creation outside the generic tool gateway and rename this gateway behavior to `validate_suggest_action`?
- Should Slack Canvas/image fetch move into task #167 rendering/context work, or should it be implemented as core `slack_api` parity first so mention context and tool calls can share it?
- Should `notify_meeting_slack` infer the linked meeting thread from meeting session state, or should Realtime/meeting tools always pass explicit channel/thread for transparency?
- Should `usage_api` remain visible while stubbed, given Peng is sensitive to product surfaces that advertise capabilities more clearly than they really work?
