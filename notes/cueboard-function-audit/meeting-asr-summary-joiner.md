## High-Level Findings

Oneesama covers the meeting core better than the early parity inventory suggested. The direct join path now has a persistent `meet-runner` JSON-RPC session, join status polling, empty-room shutdown, caption capture, post-meeting artifact generation, audio finalization, redeliver/resummarize endpoints, Slack webhook signature verification, Slack result reservation, Canvas publishing, transcript/audio upload, and Cueboard-style caption/summary parity tests.

The biggest remaining gaps are not "can it join and summarize" but "how much of Cueboard's scheduled-meeting/currying automation still exists":

- P0: ~~Cueboard's Slack meeting scanner (`startMeetingScanner` / `scanAndScheduleMeetings`) is not wired in Oneesama.~~ **RESOLVED** (`6d3f601`): Oneesama now has a config-gated Slack-agent Calendar scanner that fetches Google Calendar events, filters upcoming Meet URLs, posts a real Slack root-message approval anchor, then posts a deduped `suggest_action(join_meeting)` card in that thread. It fails closed when disabled or missing approval-channel/credential config and does not re-expose the generic `google_calendar_api` assistant tool.
- P1: Cueboard's Google Meet API client (`meetapi.go`) is not ported. Oneesama intentionally uses DOM/runner sources for participants, active speaker, captions, and artifacts. That is fine for the Realtime product, but it means official Meet conference records/transcripts/recordings are not available as a fallback.
- P1: Cueboard's Slack-side meeting copilot loop is only helper-level parity. Oneesama has Realtime in-meeting tools and copilot effect formatters, but not the old periodic `runCopilotLoop` that digests transcript deltas, opens a framework session, and performs Slack/Meet side effects from Slack agent.
- P1: Cueboard `sendMeetingChat` path is split. Oneesama has a meetd chat HTTP route and Realtime `send_meet_chat` tool, but the old Slack copilot `send_meeting_chat` registration remains product-excluded in the Slack tool matrix.
- P2: Local Whisper/Apple ASR helpers are not ported. Oneesama supports OpenAI and Gemini ASR plus captions. If offline/local ASR matters, it needs a separate product decision.

## P0 Gaps

- ~~`meeting_scanner.go:13-91` is not wired. ## P1 Gaps

- `meetapi.go:41-252` is missing. Oneesama's live-awareness feature uses Meet DOM/captions and Calendar attendee hints, but it does not fetch official Meet conference records, transcripts, participants, or recordings. This should be an explicit product decision because official API fallback would help long-meeting/post-meeting reliability.
- `watcher_copilot.go:12-184` and `meeting_webhook.go:370-834` are not ported as a running Slack-side copilot. Helper functions for deltas/effect summaries exist, but no periodic Slack-agent copilot framework session runs over transcript windows. Realtime is likely the right replacement, but the old capability should be marked `product_replaced_by_realtime`, not assumed covered by helpers.
- `asr.go:91-111` / `358-379` audio downsample/split is missing. Oneesama can consume existing `asr_chunk_*.txt` and can transcode final audio, but it does not produce ASR chunks from long recordings in this Go layer.
- ~~`meeting_handler.go:80-182` approval-card posting is blocked by the generic `suggest_action` gap from task #165.~~ **RESOLVED** (`6d3f601` plus earlier `suggest_action` side-effect work): Calendar scanner now uses the real pending-action confirmation path and stores thread-case dedupe state.
- `notify_meeting_slack` remains weaker than Cueboard's channel-user matching and linked-thread resolution. This affects meeting copilot follow-up if Realtime or Slack-side copilot is expected to notify the right Slack humans automatically.

## Product Exclusions / Route Changes

- Local Whisper.cpp and Apple ASR providers are not ported; current provider matrix is captions + OpenAI/Gemini ASR.
- Linux/Xvfb joiner launch is not ported; meet-runner is a persistent JSON-RPC session optimized for the current macOS deployment.
- Direct credentialed Google Calendar/Linear/Figma/Notion copilot tools stay excluded by task #147 product scope.
- The old Slack-side `send_meeting_chat` copilot tool is excluded from Slack tools, while the Realtime meeting surface exposes `send_meet_chat`. Keep this distinction explicit so `/slack/tools/parity` does not imply the Slack copilot path can send Meet chat.

## Open Questions

- Should Calendar-driven meeting approval be enabled in live config, or stay shipped but disabled until operators provide approval channel + Google credentials?
- Should Oneesama add the official Google Meet API client as a reliability fallback, or is DOM/runner awareness the intentional product direction?
- Is the Cueboard Slack-side copilot loop obsolete now that GPT Realtime is the strategic center, or do we still need a background Slack-side monitor for meetings where Realtime is not connected?
- Should local/offline ASR matter for OSS/private deployments, or is cloud ASR acceptable?
- Meeting approval cards now use the shared `suggest_action(join_meeting)` side-effect path; no dedicated meeting-only approval path is needed unless product wants custom card UX.
