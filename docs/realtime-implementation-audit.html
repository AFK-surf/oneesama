1 · 两套 realtime 栈（最重要的认知）

operator 栈 本轮主战场

packages/core/src/operator/ + packages/core/src/work/

  • 大脑：ConversationEnginePort + 17 种 canonical 事件；OpenAI Realtime / Gemini Live / diagnostic 三引擎。
  • 跑在哪：Node 服务进程内（operator 服务器 + 服务端工作浏览器）。
  • 音频：浏览器麦克风 PCM16 → voice WS → 引擎 → provider WS。
  • 干活：工作管线（typed job → 步进 planner → CDP 浏览器 → 验证）。

meeting 栈 既有 / 独立

packages/core/src/realtime/ + meeting/ + apps/meeting-agent/

  • 大脑：realtime-browser-bridge（mock / webrtc-mock / agents-sdk 三模式），在 Meet 页内或 sidecar 页跑。
  • 音频入：参会者音频 seam（meeting-avatar-participant-audio-stream 事件）。
  • 干活：kwwk-cu Swift helper（macOS 无障碍 AX 控制，Gemini planner）。
  • 关键：不使用 operator 栈的对话引擎，是平行实现。

RFC 的最终目标是把这两套接起来：operator 栈做"一个大脑"，meeting 栈退化为媒体端点（摄像头/麦克风/参会者音频）。这就是尚未完成的 M1–M4。

2 · operator realtime 数据通路（逐段）

2.1 Transport 选择 lan-operator-conversation-transport.ts:52

显式 MAB_LAN_OPERATOR_TRANSPORT > 检测到 OpenAI key > 检测到 Gemini key > 无 key 回落 diagnostic（mock）。key 链：ONEESAMA_OPENAI_API_KEY → MAB_OPENAI_API_KEY → OPENAI_API_KEY（Gemini 同理 + GOOGLE_API_KEY）。

2.2 语音上行 voice-client.ts:149 · surface.ts:1319

浏览器 AudioContext({ sampleRate: 24000 })（与 provider 声明的 24kHz 对齐，旧浏览器回落设备率，chunk 元数据始终带真实率）→ ScriptProcessor 切 1024 采样 → PCM16 base64 → voice WS。服务端 forwardVoiceChunk 有 32 路 in-flight 上限，超了丢弃计数；单活跃流假设（第二路流被当 stale 拒绝）。

2.3 OpenAI 适配器：会话声明 lan-operator-openai-realtime-adapter.ts:617

本轮关键修复之一——必须声明完整 audio 块（部分块会被 API 静默忽略，是首个 transcript_timeout 的根因）： 

audio: {
  input: {
    format: { type: "audio/pcm", rate: 24000 },
    turn_detection: { type: "server_vad" },
    transcription: { model: "gpt-4o-mini-transcribe" },  // 喂意图编译器
  },
  output: { format: { type: "audio/pcm", rate: 24000 } },
}

2.4 canonical 事件抽取 conversation-event-pump.ts · surface.ts:652

事件不是 push，是每 100ms 轮询 drain（drain_events 控制命令，单飞 inFlight 防并发）。provider 原始事件经映射表转成 17 种 canonical 事件，写进 80 条环形缓冲，再广播给所有 events 客户端。

4 · 本轮发现 & 修复的 bug

已修 H11 — 并发连接 thrash（语音从来连不上的真凶） …openai-realtime-adapter.ts:838

connect() 只对"已 OPEN"短路，对"握手中"直接关掉重连。32 路并发语音 chunk 各触发一次 auto-connect → 每次握手都被下一个掐死 → "WebSocket was closed before the connection was established" ×274，流一停立刻连上。修复=两个适配器各加共享 in-flight connect promise。修后 0 错、转写精确、走代理也行。残留小问题：×32 个 cosmetic engine_connected 重复事件。

已推翻 H2 — 采样率假设

实测 24kHz 和 48kHz 裸 PCM16 在 gpt-realtime-2 上都精确转写（"purple elephant seventy-seven" / "green tiger 42"）；端点容忍未声明的采样率。从 blocker 降级为卫生项（已声明格式 + 24kHz 采集 + 常驻 eval:transcription 守门）。次要：48kHz 会双触发 server VAD。

已修 快照覆盖 — inspector 测试转绿 surface-html.ts:974

服务端 debug 快照整体展开覆盖 state.conversation，心跳里的空 canonicalEvents 会抹掉客户端事件。改为：服务端环形缓冲仅在非空时权威。

新发现 · 未修 Gemini 控制命令死分支 …gemini-live-adapter.ts:761

rawControlEvent 的 if/else 两个分支返回完全相同的 { realtimeInput: { audioStreamEnd: true } }——clear_audio_buffer 与 cancel_response 没有区别处理，if 是死代码。严重度低（Gemini 是 A/B 备选，非主路径），但应补上各自的 Gemini API 语义。

5 · 风险台账（H1–H11）

# 风险 状态 要点
H1 两个 provider 都没注册 tools OPEN 模型自主调 kwwk_computer_use 路径为空；但意图编译器是主路径，故只挡"模型自主快路径"，不挡工作管线。
H2 采样率未声明/疑似错 REFUTED 实测两种率都精确转写，降级为卫生项。
H3 服务端仅允许单活跃语音流 OPEN 第二路（会议音频）被拒；挡 M2，需 per-source 流注册表。
H4 无混音器 OPEN 两路 PCM 串行 append 会损坏时间线；MVP 必须互斥切换，混音推后。
H5 后台节流冻住合成摄像头 OPEN 标签页隐藏时 rAF 停；需 watchdog + 占位画面，或 Worker+OffscreenCanvas。
H6 Meet 页连不回 operator 服务器 MITIGATED M0 实测：同机 ws://localhost 可连；跨机被 mixed-content 拦。方案=控制走 CDP、视频走页内 WebRTC。
H7 visual 信令写死二元广播 OPEN 加第三种 kind 会与 avatar 回环串线；挡 M1，需显式链路寻址。
H8 不能 replaceTrack Meet 的 sender OPEN 用 init-script 时刻装好的中继 track，换画的内容而非 track。
H9 operator 服务器无鉴权 MITIGATED 已加 MAB_LAN_OPERATOR_TOKEN 门禁（全 WS/HTTP）。真会议前置仍需 join-scoped token。
H10 每个事件广播都带整份 debug 克隆 OPEN cloneDebugState 在音频 chunk 频率下开销大；需 lean 订阅模式。
H11 并发连接 thrash 杀死语音 FIXED 本轮根因 + 修复，见上。
